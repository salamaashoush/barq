## 3. Three §4.1/§13 rows REVERSED on evidence

Each was attempted, measured, and put back. Do not re-attempt without repeating the measurement.

### The fourteen flow components, and `ssr.ts`'s twelve string adapters

They are ONE deletion blocked on ONE compiler gap. `passes::flow::admits_element` refuses any
`SpreadAttribute` before any per-prop reasoning runs, so a construct whose props arrive through a
spread stays a component call. Compiling all 131 fixtures and reading the surviving `@barqjs/core`
imports finds exactly one:

```
For: 1 — control-flow-for-keyed-spread
```

Every FORM lowers. `<For>` alone covers four keying arms and all four emit `_$each` with no import
left behind:

```
control-flow-for                    each=YES  keeps For import=no
control-flow-for-keyed-by-item      each=YES  keeps For import=no
control-flow-for-keyed-false        each=YES  keeps For import=no
control-flow-for-keyed-fn           each=YES  keeps For import=no
control-flow-for-keyed-unprovable   each=YES  keeps For import=no
control-flow-for-keyed-spread       each=no   keeps For import=YES
```

The string backend has the identical gap and the identical fallback, and all eleven of its adapters
were confirmed reachable from legal source one construct at a time (`<Show {...p}>` compiles to
`_$ssrShow`). Deleting either half turns a working program into a load-time `SyntaxError`.

**Why the element answer does not transfer.** §5.3 put a spread back on the template path for
elements, so the obvious move is to do the same here. On an element every unknown name has the SAME
KIND of destination — an attribute channel — and `_$spread` resolves each at run time through the
tables the compiler reads. On a flow construct each prop decides a DIFFERENT PART OF THE LOWERING:
the source, a second Block, one of three key expressions, and the body Block's own PARAMETER LIST,
which changes with the keying mode. `admits_value` says it for `keyed` in as many words — "the two
answers are different programs". The existing unprovable-prop rule does not stretch to cover it
either: `control-flow-for-keyed-unprovable` is a NAMED prop behind a binding, where the compiler
still knows which prop it is. A spread hides which props exist at all.

### The Block brand does not go behind `dev`

§12 asks for it on the grounds that it "allocates a closure per construction to serve two DEV
facilities". Two things are wrong with that. The closure is not a DEV facility — it establishes the
ambient owner (`currentOwner = scope`), which is C1/O4.5, and without it every `getContext`,
`onCleanup` and `effect` in the same body follows `CURRENT`. Only the `[BLOCK] = true` property
write is DEV, and a property write is not a closure.

And the cost was ablated. 100-row page, `renderToString` envelope, 51 trials × 100 iters:

| build | median µs |
|---|---|
| brand + guard (shipping) | 4.62, 4.88 |
| brand only (ablation) | 4.53, 4.74 |

The two shipping runs differ by more than shipping differs from ablated. That agrees with M5, which
measured the same thing from the other direction: "The SSR bar did NOT move with it, and the brand
was not the cause."

### `merge` stays

§13's row reads "`merge` → `mergeProps`, two names for one operation". It is wrong twice. They are
not one operation — `merge` treats a later `undefined` as a VALUE where `mergeProps` skips it, and
`props.test.ts` pins the difference in a test named for it. And the direction is backwards for the
version §13 aligns with: `@solidjs/signals` 2.0.0-beta.31 exports `merge` and has no `mergeProps` at
all; `mergeProps` is Solid 1.x's name.

## 4. The oracle, and what replaced each channel

`CODESIGN.md` §6 retires the un-compiled path on three grounds, the first decisive: both paths
rendered a blank page for `<Provider><Child/></Provider>`, so the harness was green on the very bug
that prompted the redesign.

| channel | was | is |
|---|---|---|
| rendered DOM | differential against `createElement` | a per-fixture GOLDEN — every frame plus every attribute line — beside the `-O0`/`-Ox`/`interp` differentials |
| effect counts | an upper BOUND against the oracle's count | `test/effect-counts.ts`, 131 hand-written rows, each an EQUALITY |
| node identity | differential, under a per-frame guard | metamorphic and unconditional; the differential survives only as a clean-vs-corrupted DETECTOR |
| marker layout, attribute partition | already self-checks | unchanged, in `harness.ts auditCompiled` |
| the L6 corruption self-checks | corrupted-vs-oracle | corrupted-vs-CLEAN-COMPILED |
| `ssr.test.ts`'s reference | the un-compiled path | the DOM backend — §6 L2's construction, one IR and two `Backend` impls |

**The bound becoming an equality is the substantive change.** "Fewer effects than the oracle is the
entire point of the compiler" made the old channel one-sided, so a binding that silently went
missing — target #1 over-applied — was reported as a win. `graded.ts`'s exemption count across the
whole table went **3 → 1**, and the survivor is a real defect (`leak-known-failures.ts`) rather than
a reference artefact.

Provenance of the 131 rows, stated rather than implied: seventeen fixtures already carried a
hand-written `optimality.effects`, and the `created` column agrees with all seventeen. The rest were
taken from a build the retiring oracle still passed.

## 6. Four defects the retirement exposed

Each was invisible because the thing that would have caught it was the reference.

1. **`attribute_expression` handed a JSX attribute's string literal to the runtime un-decoded.**
   `title="a &quot; b"` reached `setAttribute` as the six characters `&quot;` and serialised as
   `&amp;quot;`. It hit `element(scope, tag, props)` and every component prop; the template path was
   correct because the parser resolves references out of baked bytes. Nothing could see it: the
   reference was un-compiled, so it never went down either channel, and the one comparison that
   would have caught it compared SSR against that same reference. Re-pointing that comparison at the
   DOM backend failed on the first run.
2. **`element()`'s children were emitted eagerly.** `<table>{a()}-{b()}</table>` compiled to
   `{ children: [a(), "-", b()] }` and never updated. `fallback.rs` now thunks a non-inert `{…}`
   child of a refused element.
3. **`insert` handed an ARRAY straight to `childToNodes`**, which calls each function element once —
   so the same values were frozen at run time as well, and owned by whatever was ambient. An array
   holding a function is now one live hole. ONE effect for the whole array, which is what Solid's
   `insertExpression` does with `normalizeIncomingArray`'s `dynamic` flag, and the right shape for
   two reasons: N reads share one effect and one range instead of N of each, and N anchorless holes
   in one parent each append at the end, so the first to re-render from empty lands after its
   siblings — the interleaving `Anchor::Marker` is mandatory for.
4. **`semantics.test.ts` validated `greenAt` against `^M[0-9]$`** — single digit, which would have
   rejected every M10 row.

(3) closed half of `sem-own-given-scope-wins`'s O4.5 row: disposal now reaches the Block
(`ranCleanup` 0 → 1). The parity ratchet failed on the IMPROVEMENT and named the new digest, which
is exactly what it exists for. The remaining half — `childToNodes` still invokes the Block with
`getOwner()` rather than the `s` it was given — is rewritten in the row and moved to M10.

Two more, found while driving the app rather than by a suite: kitchen-sink had a
`const [user] = signal(…)` and two `ref={setRefSignal}` sites left over from the `useState` → `signal`
rename, each of which blanked a route with no console error. **The app is the acceptance test, not
the suite** — again.

## 7. `packages/testing` compiles its own suite now

It ran on bun's `react-jsx` transform, which lowers JSX onto `jsx`/`jsxs`. Its own components carried
a comment saying the un-compiled path "hands plain values rather than Cells" — which means the suite
was measuring a path §11 Q2 says does not exist. A `Bun.plugin` `onLoad` in its preload hands every
`.tsx` to the native transform, so what those 16 tests drive is what a user's build produces.

This is also what made deleting `jsx`/`jsxs`/`jsxDEV` possible: the only other consumers were
declaration reads in the compiler's own harness (`fixtureOptimality`, `ssrDiffers`), and those now
compile the fixture before loading it. The declarations are module-scope constants and survive the
compile untouched.
